Ben, 8 Nov: move off Nav2 one piece at a time, each beside Nav2 until it wins. The order: the costmap (done), then the path planner (this page), then the navigator. Nav2 stays the default, and stays on the car.

The short version

  • Switch: planner:=own. Package aav_planner (Rust).

  • What it is: Nav2's State Lattice planner (our default) ported: the same primitives file, the same penalties from nav2.yaml, the Reeds-Shepp finish, the smoother. It checks the car's outline on the global costmap.

  • Drop-in: it answers Nav2's own ComputePathToPose action. The behaviour trees call it instead of planner_server; nothing else changes.

  • Test lot, 3 runs each: 12 of 12 legs, as Nav2's lattice; the same paths (within a metre), the same planning time (3-5 ms a call).

  • Campus: both planners failed the same legs (MPPI gave up, not the planner); ours took about 20 % longer to plan the long legs (180 ms against 150 ms).

  • Not yet a winner: as good on the lot, a little slower on the campus.

How the swap works. navigation.launch.py remaps one name in bt_navigator: compute_path_to_pose → ours. The costmap step did the same with the clear service. navigate_through_poses still plans with Nav2's lattice (not ported yet).

What it does

start ─▶ A* over the moves ─▶ now and then: one curve straight to the goal? ─▶ smooth ─▶ path
          (primitives file)      (Reeds-Shepp; Dubins when forward only)
Step What it does Nav2's
moves 6 car-shaped moves from each of 16 headings (our file, tools/lattice_primitives.py); backwards too with reversing:=true LatticeMotionTable
does it fit? the car's padded outline at each pose along a move; most poses skip it (far from anything) GridCollisionChecker
cost of a move length × (1 + 2 × cost), × 1.05 for a turn, + 0.05 to change turn, × 2 backwards getTraversalCost
how far still? the larger of: round the obstacles (a grid search from the goal), and the car's shortest curve on open ground the two heuristics
the finish a Reeds-Shepp curve to the goal when one is clear (within 3 m), wider turns if cheaper AnalyticExpansion
smoothing pull each piece straighter, then re-join the true start and goal Smoother

Small changes from Nav2 (all in ros/drivers/aav_planner/PROVENANCE.md):

  • a node's pose changes only when a move makes it cheaper (Nav2 can mix two moves);
  • each move is checked for collisions on its own (Nav2 remembers the first move's answer for every later one). Safer, but more checks: part of why ours is slower;
  • the car's outline is checked where the path puts it (Nav2's is half a cell off).

  • Both failed the same way: at the start of "along the road" MPPI said "Optimizer fail to compute path" and Nav2 gave up (Nav2's planner 3 of 3, ours 2 of 3). The follower, not the planner: both planned the same 254 m path. Then "round the bend" started from wherever the car stopped, often too near the kerb to fit (both planners said "start occupied").
  • Ours is about 20 % slower on long legs. Likely the per-move collision checks (above). Both are far inside the 1 s replanning period and the 5 s limit.
  • TODO 140's P4-to-Fieldhouse route was not run: these legs already fail before the planner matters.

The verdict

  • As good on the test lot: the same legs, paths and times as Nav2's lattice.
  • A little slower on the campus's long legs; nothing there decides between them yet.
  • Nav2's lattice stays the default. Next: make ours faster (remember each node's check, as Nav2 does, where it is safe), and Hybrid-A* for forward only.

What's missing

  • Hybrid-A* (the forward-only default on the car): not ported. planner:=own with reversing:=false plans Dubins moves on the lattice instead.
  • navigate_through_poses still uses Nav2's planner (ComputePathThroughPoses).
  • The navigator step (next) must call ours for both, and clear our global costmap.
  • On the car: untested; the car refuses planner:=own.
