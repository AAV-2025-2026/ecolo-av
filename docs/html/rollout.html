How our code goes onto the car: the names, the order, and each computer's steps. The full steps, with sign-offs: Car day, Car setup and The ESP32 on the bench. Back up first, every time.

The names

One name per computer: its role (what car_setup.sh and the docs call it) is also its planned hostname, with aav- in front. car_setup.sh accepts the old hostname and the new one, so renaming can wait. Renaming is the hardware lead's call.

Computer Role Planned hostname Today's hostname Old nickname Keychain login
Jetson AGX Orin orin aav-orin ubuntu JETSON aav-jetson
Pi wired to the ESP32 motor_pi aav-motor ubuntu-cortex CORTEX aav-cortex
IMU and GPS Pi localization aav-localization localhost.localdomain LOCALIZATION aav-localization
Dashboard Pi (two screens) dash aav-dash aav-desktop aav-desktop
Camera Pis camera_pi aav-cam1, aav-cam2 the same CAM1-PI, CAM2-PI aav-cam1, aav-cam2
ESP32 control board (firmware) aav-esp32, only if its WiFi page is on
Velodyne lidar (no computer) aav-lidar, its name on the router

The Keychain also has aav-qnxpi: a Pi whose job we don't know. Ask the hardware lead.

To rename one, after its backup: sudo hostnamectl set-hostname aav-motor, change the old name in /etc/hosts, reboot. Then update the Keychain entry's name and hosts.txt.

What runs where

Computer Plugged in Runs Machine file
Orin the lidar (network), CAN the brain: ego, Nav2, localization, perception machines/orin.yaml
Motor Pi the ESP32 (UART) the bridge to the ESP32 machines/motor_pi.yaml; alone: motor_pi_alone.yaml
Localization Pi the IMU, the GPS (USB) their drivers only; the Orin does the maths machines/localization.yaml
Camera Pis the front cameras video streams, no ROS (Pi OS) none
Dashboard Pi the two screens the HUD and the map none
  • The ESP32 has no YAML. Its settings (steering limits, brake positions, speed limits, timeouts) are built into its firmware; its CONFIG line prints them all at boot.
  • The lidar sends its packets straight to the Orin.

The order

Monday: the ESP32 and the Motor Pi first. One step at a time; each has a way back.

# Step Where it's written The way back
0 At home: pixi run car-day-check all OK; the car kit on a USB stick A0
1 Back up: an image of the Motor Pi's SD card; the ESP32's flash (below) A2
2 The Motor Pi: our stack from the kit (below) A5 4e the SD image
3 The Motor Pi's UART ready: console off, theirs off. Needs Ben's OK A7b its table's last column
4 The ESP32: back up, flash the Rust, the first check, the checks on stands A8, pixi run esp walk flash the backup
5 Drive on stands, the joystick or the keyboard, on the Motor Pi alone A9b
6 Later: the Orin, the localization Pi, the cameras, the dashboard below each one's image

Without the Orin (steps 4-5): the Motor Pi runs everything, ~/aav-jazzy/aav.sh ros2 launch aav_bringup car.launch.py machine:=motor_pi_alone max_speed:=0.3. Its output mux sends the heartbeat the ESP32 needs. Never run the Orin's stack at the same time.

The ESP32 (a USB cable, from a laptop with the repo)

pixi run esp tools                       # once per laptop
vendor/cargo-tools/bin/espflash read-flash 0 0x400000 backup-esp32.bin
                                         # the backup of the C++ (4 MB): a secret inside, never in git
pixi run esp walk                        # talks you through: the flash, the first check
  • What goes on the board: car-day/esp32/spine-esp32-umod-v2.elf, made by pixi run car-day-build (version 2 frames, no uplink: Day A's choice).
  • The way back to the C++: vendor/cargo-tools/bin/espflash write-bin 0 backup-esp32.bin, and frame_version: 1 again on the Motor Pi.

A Pi with Ubuntu (motor_pi, localization, dash)

# an image of the SD card first; the kit copied over: scp -r car-kit <user>@<address>:~/
bash ~/car-kit/car_setup.sh <role>                 # a dry run: read what it will do
bash ~/car-kit/car_setup.sh <role> --apply         # do it: backup, upgrade, install, services, check

The Motor Pi on Monday takes only three steps: bash ~/car-kit/car_setup.sh motor_pi backup install check --apply.

  • No upgrade: it keeps Ubuntu 22.04 until the Rust ESP32 has passed car day's session 6 (--after-esp32). Its old bridge is the way back to the C++.
  • No services yet: it refuses while the old bridge starts at boot. After A7b, start ours by hand (A7b step 6); services --apply once the team agrees.

A Pi with Pi OS (the camera Pis: they stay on Pi OS)

# an image of the SD card first
bash car_setup.sh camera_pi upgrade --apply
bash car_setup.sh camera_pi services --apply

The Orin

# a full image first (NVIDIA's backup, from a host PC): car-day.md B3
bash car_setup.sh orin                   # a dry run
bash car_setup.sh orin --apply

Later (Day B): the reflash to JetPack 7.2, then car_setup.sh orin again. Not yet run on the real Orin.
