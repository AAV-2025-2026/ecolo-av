Every backend takes the same /ego/actuator_cmd, so the drivers, mux, ego and localization run unchanged whether the "car" is a turtle, Gazebo, or the real thing. Climb the ladder one rung at a time.

pixi run sim and pixi run turtle stay on this computer: other terminals here see them, other computers don't. So a simulated car never meets the real one. To share one on purpose: ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET pixi run sim.

The test ladder

Rung Runs Proves
1. Unit tests: pixi run test the maths and protocols, without ROS ego's maths, the CAN frames, the spine logic
2. turtlesim: pixi run turtle mux, ego, scripted driver, ekf_local the command path, end to end
3. Gazebo: pixi run sim the whole stack, on a simulated car with an IMU and GPS localization and Nav2
4. Replay localization (and Nav2) on a recorded drive config changes, against real sensor data
4b. The bench: pixi run bench the car's own graph: the spine bridge and CAN frames, the spine's firmware logic on a model car, pretend sensors the car's software path, end to end, before the car: Bench mode
5. Car on stands the real backend, wheels off the ground the firmware link, signs and limits
6. Car everything, with a safety driver the phase you're on

More drivers in the turtle run

Joystick: plug it in, start with pixi run turtle teleop:=true, hold the deadman (the trigger) and steer.

Scripted drive: speed up, hold, slow down, on a gentle left curve:

ros2 action send_goal /scripted_drive aav_interfaces/action/ScriptedDrive \
  "{target_speed: 1.0, acceleration: 0.5, deceleration: 1.0, hold_time: 3.0, curvature: 0.2}" --feedback

The keyboard or joystick overrides the script at once. Let go, and the script carries on.

E-stop: ros2 topic pub --once /safety/estop std_msgs/msg/Bool "{data: true}" blocks every driver. Publish false to clear it.

Gazebo

pixi run sim                     # the empty world, with Nav2
pixi run sim world:=test_lot     # the walled test lot, with its map
Argument Default Means
world empty empty or test_lot
nav true start Nav2
teleop false true with a joystick plugged in
gui true show the Gazebo window (on a Mac, as a second program)
follow true point the window's camera at the car
rviz true open RViz

How the simulated car connects:

  • Gazebo plays the car, with Ackermann steering, an IMU and a GPS.
  • gazebo_adapter turns those into the real drivers' topics: /vehicle/odom, /sensors/imu/data_raw and /sensors/gps/fix.
  • The IMU filter, both EKFs and navsat_transform run with the car's own configs, on simulated time.
  • Map (0, 0) is where the car starts, facing east.

To drive it:

  • Keyboard: pixi run keyboard --sim.
  • A Nav2 goal: in RViz, click 2D Goal Pose, then click and drag on the map. Any human input overrides Nav2.

No GPU, or in a virtual machine?

Start it with gui:=false, and watch in RViz or Foxglove instead.

The car never appears?

If the log keeps saying Requesting list of world names, Gazebo's programs can't find each other: they use multicast, and some networks and firewalls block it. Run export GZ_IP=127.0.0.1 in every terminal, then start again. On a shared computer, also set your own GZ_PARTITION=<any name>, so your simulator doesn't meet someone else's.

Replay a recorded drive

On the car, record a drive: tools/record.sh parking_lot_test writes bags/<date>_parking_lot_test/. Then re-run localization against it on any laptop:

ros2 launch aav_bringup replay.launch.py
ros2 bag play bags/<the bag> --clock --topics /vehicle/odom /sensors/imu/data_raw /sensors/gps/fix /tf_static

A bag from Gazebo carries simulated time. Play its own /clock instead of --clock: ros2 bag play bags/<the bag> --topics /clock /vehicle/odom /sensors/imu/data_raw /sensors/gps/fix /tf_static. pixi run tools/ros.sh python3 tools/check_graph.py --profile replay checks the result.

Change an EKF setting, replay, compare the path. That's how to tune localization without the car.

tools/replay_commands.sh bags/<the bag> plays the recorded commands back into the mux as replay (priority 40). It's open loop, so the car drifts from the original path.

CARLA: parked

  • What it is: a full self-driving simulator, with towns, traffic and photoreal cameras. It's the right tool for testing cameras.
  • Two versions: CARLA 0.9.16 (Sept 2025) runs on Unreal Engine 4; CARLA 0.10 (Dec 2024) on Unreal Engine 5, and it's heavier.
  • Why not now: its built-in ROS 2 link stalls on Jazzy (issue 9551); the fix was closed without merging on 26 May 2026. It has no Mac version, and wants an NVIDIA GPU with 8 GB or more.
  • Parked (10 Oct): Gazebo and bench mode already drive the whole car graph: Nav2, the sensors and the e-stops. If perception needs realistic streets later, it can run on the team's NVIDIA Linux machine, once it supports Jazzy (Q31).
  • Ours: aav_carla is a stub that has never run.

When nothing moves

Work down the chain:

# Ask Check
1 Is a driver publishing? ros2 topic hz /drivers/keyboard/cmd_vel (or joy, scripted, nav)
2 Did the mux pick it? ros2 topic echo /control/cmd_vel. If it's silent, look for a latched e-stop: ros2 topic echo /safety/estop
3 Is ego converting it? ros2 topic echo /ego/actuator_cmd: it's always 50 Hz, so look at the speed
4 Is a backend listening? ros2 topic info /ego/actuator_cmd -v
5 In Gazebo or replay: is everything on sim time? a node on wall-clock time ignores sim-time messages
6 Does the graph match the contract? pixi run check sim (or replay)
