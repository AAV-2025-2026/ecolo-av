# The debug HUD: what the car sees, and what it thinks

* **Author:** Ben (the ask), written up 29 Oct 2026
* **Status:** Proposed (EGM review next)

Ben, 29 Oct: "I guess we call the low level hud a debug hud and it should connect directly
to the ros node at the sensor and or actuator." "When we run pixi run debugdemo we want the
same gazebo that shows up but the hud now shows the ndt or occupancy network. maybe even
allows us to swap algorithms." Earlier (28 Oct): "I want to see the occupancy network",
"put it on a hud like we have".

## The idea in one line

A second raylib program, `debug_hud`, beside the in-car `hud`: a 3D view of the lidar's
**cubes** around the car, with the localizers' guesses on top, and a side panel of every
sensor and actuator **straight from its own node**. `pixi run debugdemo` is `pixi run demo`
with `debug_hud` in place of `hud`.

## What it shows

```
┌───────────────────────────── 3D view (orbit with the mouse) ─────────────┬─ panel ──────┐
│  cubes: 20 cm, coloured by height, fading when not seen for 2 s           │ IMU  50 Hz ✅│
│  the car (its outline from vehicle.yaml)                                  │ GPS   1 Hz ✅│
│  where each localizer thinks the car is:                                  │ lidar 10 Hz ✅│
│    EKF local (blue), EKF global (green), AMCL (orange + particles),       │ wheels   ✅  │
│    Gazebo truth (white, sim only), NDT (purple, later)                    │ spine: ARMED │
│  Nav2's plan (yellow)                                                     │ steer +0.12  │
│  objects: touching cubes joined, a box and a size (later: a name)        │ thr 0.20 brk0│
│                                                                           │ tracker: lqr │
└───────────────────────────────────────────────────────────────────────────┴─ keys 1-5 ───┘
```

| Layer | From | Today? |
|---|---|---|
| Cubes | `/sensors/lidar/points` (PointCloud2, lidar_link), placed with `/localization/odom/local` | new |
| Objects | the cubes, joined (flood fill over touching filled cubes) | new |
| EKF local, global | `/localization/odom/local`, `/localization/odom/global` | exists |
| AMCL + particles | `/localization/amcl/pose`, `/localization/amcl/particles` (trials) | exists (trials) |
| Truth | `/vehicle/gazebo/truth` (sim only) | exists |
| NDT | `/localization/ndt/pose` | later: its own design |
| Plan | `/plan` | exists |
| Sensor panel | each sensor's own topic, not the muxes': rate, last value, age | exists |
| Actuators | the spine's or bridge's status: armed, mode, steering, throttle, brake | exists |
| Tracker | `/drivers/nav/track/status` | exists (trials) |

## Swapping algorithms live

| Key | Does |
|---|---|
| 1-5 | the tracker: pure pursuit, Stanley, LQR, MPC, or back to Nav2's own controller |
| C | cubes on/off; L each localizer layer on/off |

The tracker keys set `aav_track`'s `tracker` parameter (a ROS parameter service call). That
needs one change in `aav_track`: change trackers at run time, between ticks, resetting the
new one on the current path. "Back to Nav2's controller" is not possible live (it's a
launch-time remap), so key 5 only says so. The debug HUD **never commands an actuator**:
moving the car stays with the drivers and the spine's test mode (TODO, preflight on stands).

## Where the code lives

| Part | Crate | ROS? raylib? |
|---|---|---|
| The voxel grid, fading, flood fill, colours, the layers' state | `ros/hud/aav_hud/crates/debug-core` (new) | neither: tested on a laptop |
| PointCloud2 bytes → points (x, y, z float32 fields, by offset) | `debug-core` (`cloud.rs`) | no: plain bytes in, points out |
| The window and the node | `ros/hud/aav_hud/crates/debug-app` (new), binary `debug_hud` | both |

No new crates from crates.io: raylib and rclrs as `hud` uses them. The cloud is parsed from
its bytes by field offset (no `ros_pointcloud2`, so no new dependency for now).

**No TF in rclrs.** Points go from lidar_link to base_link with the fixed mount in
`vehicle.yaml` (`sensors.lidar_link`), then to `odom` with the local EKF's pose. That is
what TF would do for a rigid mount; the debug HUD says so in its README.

## Limits, so it stays fast

| Thing | Limit | Why |
|---|---|---|
| Cubes kept | within 30 m of the car; at most 50,000 | a 20 cm grid of a 60 m square is 90,000 columns |
| Points per cloud | every point (28,800 at 10 Hz) | a hash insert each: well under 10 ms |
| Drawing | one instanced cube mesh, or raylib's `draw_cube` with a cap of 20,000 | raylib on a Mac's GPU |
| Fading | a cube not hit for 2 s fades over 1 s, then goes | moving things leave no trail |

## `pixi run debugdemo`

`tools/demo_all.sh debug`: the same as `pixi run demo` (Gazebo in the walled test lot, the
nav screen, the street-map window) with `lidar:=true amcl:=true tracker:=pure_pursuit
reversing:=false`, and `debug_hud` in place of `hud`. Local only (`tools/ros.sh --local`),
like every stand-in.

## Order

1. `debug-core`: grid, fading, cloud parsing, flood fill, with tests.
2. `debug-app`: the 3D view with the cubes and the car; then the layers; then the panel.
3. `aav_track`: live tracker swap (parameter callback), with a test.
4. `pixi run debugdemo`, the README rows, `docs/hud.md`'s section, a features.md row.
5. Later, its own design: NDT (`ros/localization/aav_ndt`, Rust), drawn as a layer.
