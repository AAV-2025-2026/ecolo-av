## Sensor findings (camera, LiDAR, IMU, GPS)

### Camera (aav-cam2, .118) — the "freezes after ~20 min" — **a CONFIG problem, not hardware**

Verdict after checking the evidence: **two configuration faults, no bad parts.**

1. **USB autosuspend is on, and the camera is asleep.** `power/control = auto`,
   `autosuspend_delay_ms = 2000`, and the device's `runtime_status` reads **`suspended`**
   right now. This is the classic "streams fine, then freezes" cause — the webcam is powered
   down when it isn't being actively read, and the stream stalls. Pure power-management
   config.
2. **The stream points at the wrong device node.** `cam1`'s ffmpeg is hardcoded to
   `/dev/video0`, but the webcam is `/dev/video1`. On a fresh boot it may enumerate as
   `video0` and work; after any re-enumeration it becomes `video1` and ffmpeg can never
   reopen it (restart loop, errors every ~6 s).

**Evidence it is not hardware:**

- USB disconnect / re-enumerate events in `dmesg` happen **only in the first 97 seconds of
  boot**; none since. Uptime at inspection was **~1h44m** with the camera stable on the bus
  throughout. So the boot re-enumerations are normal startup settling, **not** an ongoing
  brownout. (Earlier in the session this was mis-read as a bad cable from the boot resets
  alone; the uptime data corrects that.)
- A live capture returned **"Device or resource busy"** (not "no such device") — the camera
  is present and claimed, by MediaMTX's restart-loop ffmpeg.
- The Pi is healthy: 67.5 °C, `throttled=0x0` (no under-voltage), 6.7 GB RAM free.
- `cannot get freq at ep 0x84` is a benign UVC message (the webcam exposes an audio/mic
  endpoint); harmless.

**Fixes (all software, no parts):**

1. Stop the camera sleeping: set its USB `power/control = on` (a udev rule), or boot with
   `usbcore.autosuspend=-1`.
2. Point `cam1` at the stable by-id node instead of `/dev/video0`:
   `/dev/v4l/by-id/usb-Arducam_Technology_Co.__Ltd._USB_Camera_SN0001-video-index0`.
3. Optional: a glance at the USB cable/port, since there were a few boot-time resets (not the
   cause of the freeze, but worth ruling out over time); clean the stray `paths:` key.

- **Streams unicast to `192.168.1.140`** (data UDP 2368, telemetry 8308). That's why a sniff

### IMU & GPS — **not publishing (the real problem)**

- The only live ROS participant on the reachable network is **.211, on ROS domain 0**.
- It **subscribes** to `/carla/ego_vehicle/imu`, `/carla/ego_vehicle/gnss`,
  `/carla/ego_vehicle/speedometer`, `/carla/ego_vehicle/ackermann_cmd` and
  `/battery_status` — and **nothing publishes any of them** (publisher count 0; `ros2 topic
  hz` saw zero messages).
- These are **CARLA-bridge topic names**: this node is wired to consume a CARLA simulator /
  carla-style bridge that isn't running. So on the car's live ROS graph **there is no IMU
  data and no GPS data flowing at all.**
- The LiDAR's own GPS input being off/absent fits: the **GPS subsystem (ZED-F9R on the
  RTK-Pi) appears not to be running or not publishing**.
- **Can't go further read-only** — need logins to the sensor machines to find the IMU,
  GPS/NTRIP and Velodyne drivers and see why they're silent.

## How this was found (read-only, mostly without logins)

Only the camera Pi could be logged into. Everything about the other machines came from the
network itself:

- **Ping sweep + `arp -a` + a TCP port probe** — the host list, OSes (from SSH banners), and
  open ports. `pixi run net-map` does this.
- **DDS / ROS 2 discovery** — ran `ros2` (Jazzy, via pixi) with `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET`
  on domains 0 and 10 to list the live ROS graph, and a small Python listener on the RTPS
  SPDP multicast group (`239.255.0.1`, port `7400 + 250·domain`) to map which **IP** each
  ROS participant is. Node names came back `_UNKNOWN_` (the car runs a different ROS distro —
  Humble — so only the DDS endpoints are visible, not the ROS-level metadata), but topics,
  publisher/subscriber counts and participant IPs are reliable.
- **The LiDAR's web API** — `http://192.168.1.201/cgi/{info,status,settings}.json` gave its
  model, state and, crucially, its data destination.
- **Passive UDP listen** on the LiDAR data ports (2368 / 8308) — confirmed it is unicast, not
  broadcast.

**ROS graph seen (domain 0):** one participant at **.211** that *subscribes* to
`/carla/ego_vehicle/{imu,gnss,speedometer,ackermann_cmd}` and `/battery_status`, publishing
only `/rosout` and `/parameter_events`. No other domain (0–39) had any non-laptop
participant. The Foxglove bridge on **.140** is up (port 8765) but did not appear as a ROS
participant on domain 0 — it is on another domain, or its ROS graph wasn't running.

**LiDAR settings (`/cgi/settings.json`):** `host.addr = 192.168.1.140`, `dport 2368`,
`tport 8308` — so the LiDAR sends to **.140**. `net.addr = 192.168.1.201`, static (dhcp off),
gateway .1. GPS/PPS receive off.
